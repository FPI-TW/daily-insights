## 三項發現與修正

### 過期分析仍提交其他資料列的修改

原本 `run_claimed` 在 `settle_success` 回傳 false 後仍 commit。舊分析雖然無法覆寫事件標題，
卻會提交 handler 直接更新的各市場「為何重要」，使新舊結果混用。

修正後，過期成功結果會回滾整個 handler transaction，只有 LLM 呼叫紀錄另存，避免遺漏已發生的用量。
回歸測試使用真正的分析 handler，驗證新標題、繁中與簡中理由均不被舊工作覆寫，且兩次呼叫紀錄都保留。

### 重排後 attempts 重用導致舊工作被誤認為新工作

原本 attempts 同時代表重試次數與工作識別。A 取得 attempt 1、重新排入、B 再取得 attempt 1 時，
A 的舊結果可以通過 fence 並完成 B 的工作。不計次數的額度等待也會重用 attempts。

每個 stage 現在有獨立 UUID claim token，每次領取都換新 token；重新排入、暫停及結算時清除。
成功、重試、額度等待與致命錯誤均須符合 token、attempts 與 pending 狀態，否則回傳 fenced，
也不觸發舊工作的失敗／額度通知。重播工具的手動領取同步寫入 token。

回歸測試涵蓋重排後四種結算路徑，以及額度等待重用 attempt 數字的情境；原有重試上限測試維持不變。

### 不同日期共用新聞 URL 時，較新版次沒有來源連結

原本歷史 import 依日期與 URL 建立事件，但文章的 URL hash 全域唯一，無法同時連到不同日期的事件。
較新事件因此沒有文章關聯，讀者 API 的 sources 會是空列表。

修正 `0034` 在刪除舊表前，為每個歷史事件保存 `legacy_sources`（原來源名稱、URL、發布時間）。
讀者 API 合併快照與文章來源並依 URL 去重，保留文章 URL 全域唯一的收稿規則。
回歸測試涵蓋兩個日期、三個市場、三種語言，以及原文章已被其他事件佔用的情境。

### P2：事件合併沒有轉移來源快照

- 位置：`modules/newsroom/public_api.py:167–176`；整合點為 `events_service.merge_events`。
- 讀者 API 只讀取目前事件的 `legacy_sources`。合併程式會搬移文章與版次項目，但不會搬移這次新增的來源快照。
- 已重現：某 URL 的文章屬於前一天，當天歷史事件 B 僅靠快照保留該 URL。合併 B 到當天事件 A 前，版次具有 A、B 兩個來源；合併後目標事件只剩 A 的來源，B 的快照仍留在已合併事件上，來源再次遺失。
- 建議：合併時同步合併、去重來源快照，並處理目標事件不是 `created_by = legacy` 的情況；補上 snapshot-only 來源合併至 legacy／非 legacy 事件的回歸測試。原第三項的直接讀取案例已修正，但尚未涵蓋這個後續操作。

### P2：已跑過原始 import 的資料庫無法直接降級

- 修正版 `0034.downgrade` 無條件刪除 `legacy_sources`。已部署原始 `0034`、目前在 `0053` 且尚未跑新版 `0054` 的資料庫沒有此欄位。
- 已重現：模擬原始 `0053` schema（沒有來源快照欄位），直接執行 `alembic downgrade 20261001_0033`，在 `ALTER TABLE newsroom_events DROP COLUMN legacy_sources` 發生 `UndefinedColumn`，降級失敗。原有測試先升級 `0054` 才降級，沒有覆蓋此路徑。

## 後續修正與最終複查（2026-10-29）

### 來源快照的合併與拆分

`events_service.merge_events` 在既有事件鎖與同一交易內，把來源事件的快照合併到目標事件，
依 URL 去重，優先保留目標的名稱與發布時間。讀者 API 不再以 `created_by = legacy` 限制快照讀取，
因此合併到初篩或拆分建立的事件、以及再次合併到第三個事件，都會保留來源。

同步檢查拆分的後續操作：對應所選文章 URL 的快照隨文章移到新事件，沒有文章關聯的快照留在原事件，
避免快照繼續把已拆出的文章列為原事件來源。

新增三個合併回歸案例（legacy／triage／split 目標），涵蓋跨日期共用 URL 的 snapshot-only 來源、
目標來源資料優先、文章與快照去重、跨 session 持久化，以及連續合併；另有一個拆分快照歸屬案例。

### 原始 schema 直接降級

`0034.downgrade` 改用 `DROP COLUMN IF EXISTS`，支援尚未套用 `0054`、沒有快照欄位的原始資料庫。
新增回歸測試模擬原始 `0053` schema，直接降級至 `0033`，確認歷史匯入資料已移除且快照欄位不存在，
再升級至 head。原有修正版 schema 的升降級與回填案例維持通過。
