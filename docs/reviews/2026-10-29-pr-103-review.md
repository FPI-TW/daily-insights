## 三項發現與修正

### 過期分析仍提交其他資料列的修改

原本 `run_claimed` 在 `settle_success` 回傳 false 後仍 commit。舊分析雖然無法覆寫事件標題，
卻會提交 handler 直接更新的各市場「為何重要」，使新舊結果混用。

修正後，過期成功結果會回滾整個 handler transaction，只有 LLM 呼叫紀錄另存，避免遺漏已發生的用量。
回歸測試使用真正的分析 handler，驗證新標題、繁中與簡中理由均不被舊工作覆寫，且兩次呼叫紀錄都保留。

### 重排後 attempts 重用導致舊工作被誤認為新工作

原本 attempts 同時代表重試次數與工作識別。A 取得 attempt 1、重新排入、B 再取得 attempt 1 時，
A 的舊結果可以通過 fence 並完成 B 的工作。不計次數的額度等待也會重用 attempts。

每個 stage 現在有獨立 UUID claim token，每次領取都換新 token；重新排入、暫停及結算時清除。
成功、重試、額度等待與致命錯誤均須符合 token、attempts 與 pending 狀態，否則回傳 fenced，
也不觸發舊工作的失敗／額度通知。重播工具的手動領取同步寫入 token。

回歸測試涵蓋重排後四種結算路徑，以及額度等待重用 attempt 數字的情境；原有重試上限測試維持不變。

### 不同日期共用新聞 URL 時，較新版次沒有來源連結

原本歷史 import 依日期與 URL 建立事件，但文章的 URL hash 全域唯一，無法同時連到不同日期的事件。
較新事件因此沒有文章關聯，讀者 API 的 sources 會是空列表。

修正 `0034` 在刪除舊表前，為每個歷史事件保存 `legacy_sources`（原來源名稱、URL、發布時間）。
讀者 API 合併快照與文章來源並依 URL 去重，保留文章 URL 全域唯一的收稿規則。
回歸測試涵蓋兩個日期、三個市場、三種語言，以及原文章已被其他事件佔用的情境。

### P2：精選重試忽略 Retry-After 與額度等待語意

- 位置：`apps/api/src/daily_insights_api/modules/newsroom/assembly.py:1530–1532`。
- `_rate` 捕捉 `RetryableStageError` 後，固定依 `EDITOR_RETRY_DELAY` 等待 5 秒，
  沒有使用 `retry_after` 或 `counts_attempt=False`。因此 queue 對 Go 額度耗盡的等待機制
  沒有套用在此路徑；供應商已明確要求等待時仍連續發出相同請求，三次失敗後進入 fallback。
- 重現：單一市場精選回傳 `editor_provider_usage_limit`、`retry_after=5 小時`、
  `counts_attempt=False`，實際呼叫三次，中間只等待 `[5, 5]` 秒。
- 建議：尊重供應商的最早重試時間；額度等待可保存後續重試時點，或本次直接採 fallback，
  避免阻塞組稿數小時及在等待期間繼續發送必然失敗的請求。其他市場也應共用已知的供應商等待狀態。
